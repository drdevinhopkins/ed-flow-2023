# ED Flow Agent

This repository contains the Jewish General Hospital Emergency Department flow forecasting and operational analytics project.

These instructions apply to Hermes Agent and other coding/analysis agents working in this repository.

## Mission

Help interpret, validate, improve, and operationalize ED flow forecasts while protecting the production workflow.

The agent should distinguish between:

- production forecasting;
- validation/backtesting;
- experimental feature engineering;
- operational interpretation of forecast outputs.

When the user asks for an operational summary, prefer clear ED language over data-science terminology.

## Safety around production

Production is conservative by default.

- Do not modify production workflows, timers, forecast publishing, Dropbox destinations, model routing, or production feature flags unless the user explicitly asks.
- Experimental work should be additive and isolated whenever practical.
- Do not silently replace validated production routes with experimental ones.
- Weather routes remain opt-in until forecast-time weather validation is sufficient.
- Never fabricate a forecast when current data are missing, stale, or incomplete.
- If a local LLM or other presentation layer fails but deterministic forecast data are valid, fall back to deterministic interpretation rather than failing the entire workflow.

## Time zone

Operational timestamps should be interpreted and presented in `America/Montreal` local time unless the user explicitly requests otherwise.

## Current hourly forecast

The current explainable hourly forecast is generated by:

```text
scripts/hourly_forecast_v2_1.py
```

Its preferred output is:

```text
forecast-v2.1.csv
```

The forecast contains recent observed history and the next 24 hours for these targets:

- `Total_TBS` — total patients to be seen across the ED
- `POD_TBS` — patients to be seen in POD
- `Vertical_TBS` — patients to be seen in Vertical
- `TTStr` — total stretcher occupancy / stretcher burden
- `Overflow` — overflow burden
- `WAITINGADM` — patients waiting for admission
- `TRG_HALLWAY1` — triage hallway occupancy
- `TRG_HALLWAY_TBS` — patients to be seen in the triage hallway

Prefer human-readable names in routine prose.

## Explainability semantics

`forecast-v2.1.csv` contains a routed forecast and a history-only Chronos baseline.

For future rows:

```text
feature_effect = forecast - baseline_forecast
```

This is an **associational scenario contrast, not a causal effect**.

Acceptable:

> Staffing context raises the forecast by about 2 patients versus the history-only baseline.

Not acceptable:

> The staffing schedule causes 2 extra patients to be waiting.

Do not name individual physicians in routine operational summaries when physician-effect features contribute to a staffing scenario. Refer to `staffing context` or `staffing-structure context` unless the user explicitly requests physician-level analysis.

## Forecast interpretation principles

When interpreting flow, emphasize operational relationships rather than reciting every metric.

Examples:

- Total TBS falls while `WAITINGADM` rises → front-end pressure is easing while boarding pressure builds.
- Total TBS is stable while `TTStr` rises → overall demand is stable but the department is becoming more stretcher-heavy.
- POD falls while Vertical rises → burden is shifting from POD toward Vertical.
- Triage hallway pressure rises despite stable Total TBS → front-end congestion is worsening despite stable overall demand.

Do not force a dramatic narrative when the forecast is stable.

## Skills

Reusable workflows live under `skills/`.

For requests such as:

- `flow blurb`
- `hourly flow blurb`
- `summarize the ED forecast`
- `what does the flow forecast look like?`
- `how are we looking tonight?`
- `how are we looking overnight?`
- `give me the operational forecast`

load and follow:

```text
skills/hourly-forecast-blurb/SKILL.md
```

The skill is the source of truth for calculating and writing the routine hourly forecast blurb.

Future specialized workflows should be added as separate skills rather than expanding this file indefinitely.

## Guiding principle

**Compute first, narrate second.**

All numeric and temporal claims should come from deterministic analysis of the current forecast output. LLM-generated prose is presentation, not the source of truth.
